# Memory Banks — Project Idea

> Это «зачем», а не «как». «Как» — в [AGENTS.md](./AGENTS.md), в коде `.flue/` и `src/`.

## Идея в одном абзаце

`memory-banks` — это сервис на базе Flue, который держит в порядке несколько
персональных «банков памяти». Банк памяти — это просто папка с
markdown / html / txt файлами (плюс случайные бинарные вложения), которая
со временем разрастается из заметок, статей, скриншотов, выгрузок и любого
другого хлама, который пользователь хочет сохранить. Каждый банк — это
отдельный git-репозиторий, чтобы вся история раскладок была версионирована.
Сервис не пытается быть Notion'ом, Obsidian'ом или базой знаний на эмбеддингах:
файлы остаются файлами на диске, любым редактором их можно посмотреть, любым
скриптом — обработать.

## Откуда растёт

Идея отжата из практики работы с Obsidian-вольтом, где жил агент с инструкциями:
была папка `_raw/`, туда можно было закинуть что угодно, агент при запуске
обходил инбокс и раскладывал по своим местам. Подход оказался настолько живучим,
что родилось желание выкинуть сам Obsidian (он, как выяснилось, никак не
обязателен — markdown-файлы прекрасно живут на диске сами по себе) и обобщить
паттерн на несколько независимых банков для разных проектов.

## Базовые принципы

1. **Файловая система — источник правды.** Никаких баз, никаких индексов в
   отдельных хранилищах. Всё, что знает банк, лежит у него в папке.
2. **Много банков, не один.** У пользователя несколько контекстов (рабочих
   проектов, личных тем), и они не должны мешаться. Имя банка — обязательный
   аргумент API.
3. **Git как машина времени.** Каждое движение агента — это коммит. Откатить
   ошибку — один `git reset`.
4. **Агенты, а не индексаторы.** Раскладкой и поддержанием порядка занимается
   LLM. Структуру папок придумывает он сам, по мере накопления контента, не
   по жёсткой схеме сверху.
5. **Структура эволюционирует, а не дизайнится заранее.** Стартовый scaffold
   минимальный (`_raw/` + `_index.md`). Подпапки появляются, когда есть что в
   них класть.

## Роли агентов

- **Librarian (бывший Curator, первый агент).** Принимает входящие данные через API (текст
  inline или ссылки `file://` / `https://`), копирует в `_raw/`, осматривает
  текущее состояние банка и решает, куда что положить, какие индексы обновить,
  где эволюционировать структуру. Применяет план, коммитит.
- **Retriever (следующий, ещё не сделан).** Получит на вход запрос и будет
  вытаскивать из банка релевантные куски — для людей или для других агентов
  (потенциально как MCP-tool / RAG-источник).

## Языковая политика

- **Пользовательский контент** сохраняется на оригинальном языке (русский
  остаётся русским, английский — английским, иврит — ивритом).
- **Многоязычный микс внутри одного айтема** переводится целиком в английский
  (чтобы не получалось мусора на стыках).
- **Служебные файлы**, которые агент создаёт сам — индексы, глоссарии,
  описания, README, frontmatter — всегда на английском.
- **Имена файлов** в каноничных местах банка — kebab-case на английском.

## Что осознанно НЕ делаем (v1)

- Никаких векторных хранилищ / эмбеддингов. Куратор работает над сырым текстом
  и деревом папок.
- Никакого pull/push в remote-репозитории. Git только локальный.
- Никаких блокировок. Один пользователь, последовательные вызовы — гонок не
  ожидаем.
- Не лезем в существующие Obsidian-вольты пользователя. Свой root, своя
  структура.
- Не делаем UI. API + командная строка достаточно.

## Что хочется потом

- Retriever-агент.
- Доступ к банкам как к MCP-серверам для других агентов.
- Опциональный sync git remote для синхронизации между машинами.
- Метаданные (frontmatter, теги), которые retriever будет понимать.
- Возможно — простой Web UI / chat-интерфейс поверх двух агентов.
